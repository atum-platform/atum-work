# Work provider fallback

The November 28 owner request asked whether Work can switch providers when quota runs out. The engine applies the opt-in order to interactive Work turns on their existing host and keeps the manually selected model as the preferred route. Each substitution uses the normal T3 provider handoff in the same visible thread. At the next dispatch, a reset or newer matching quota evidence makes the preferred route eligible again. No provider calls are made to probe quota.

## Composer and settings contract

- In [settings.ts](../../packages/contracts/src/settings.ts), `ServerSettings.providerFallbackOrder` is `ReadonlyArray<ProviderInstanceId>`, with a decoding default of `[]`. Save the ordered provider **instance IDs** through the existing server settings update. This setting applies to Work on that host.
- In [commands.ts](../../packages/client-runtime/src/operations/commands.ts), pass `providerFallbackOrder?: ReadonlyArray<ProviderInstanceId> | null` to `updateThreadMetadata`. A list replaces the account order for that thread, `[]` disables fallback, and `null` inherits the account order. Omit the property when editing unrelated metadata.
- Read `EnvironmentThreadShell.providerFallbackState?: ProviderFallbackState` from the existing shell subscription. The [wire type](../../packages/contracts/src/orchestrationV2.ts) has `activeProvider` and `preferredProvider` as `ProviderInstanceId`, `exhaustedUntil` as an ISO timestamp, `"unknown"`, or `null`, `reason` as `"usage_limit"` or `null`, and `canContinue` as a boolean. The shell also carries the thread override. Use effective Work settings to gate the fallback UI. Quota errors can surface on legacy or opted-out threads via the same shell. An elapsed timestamp is past the recorded wait. Admission rechecks provider availability on the next eligible send.
- Use `thread.modelSelection` for the active model. On regular sends the composer may keep passing the current model selection or omit it. An explicit model selection command makes that choice the new preferred model.
- For Continue, call the existing `startThreadTurn` with the current `threadId`, `dispatchMode: "start"`, `manualContinuationOfRunId: thread.latestRun.runId`, and an empty user message and attachments. The server validates the run again and can reject stale or blocked requests. When a portable provider handoff carries the previous goal, the destination receives the native continuation prompt. The initial task is represented in the handoff history.

## Scope and verification

The first slice uses connected Codex, Claude Code, Antigravity (including its Gemini API-key mode), and OpenCode Go offers. The engine considers the first listed instance per driver and uses its advertised default model, or first eligible model when no default is advertised. Routing uses the native usage windows and settled root quota failures. The engine leaves slash commands, new context sessions, attachments, structured-output requests, guests, agent-originated work and Code projects on their normal paths. Work with an unresolved runtime request or an unsafe native handoff stays subject to T3's existing guards. Work's configured order suppresses scheduled usage-limit recovery so it cannot independently restart the same run.
